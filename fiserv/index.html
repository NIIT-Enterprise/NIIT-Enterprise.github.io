Context

as provided by client

For Business Analysts, Project Managers and Program Managers, the challenge in Agentic AI is rarely writing code; it is controlling intent. Agentic systems can retrieve knowledge, invoke tools, make intermediate decisions and continue autonomously toward a goal. GitHub Spec Kit provides a structured process that keeps business intent and evidence ahead of implementation.

The program was designed as a six-hour, non-coding project-readiness bootcamp in a Fiserv-aligned payments domain. It is now extended to eight hours with a two-hour LLM Basics block at the start, so that participants understand how large language models and coding agents behave before they write the specifications those agents will act on.

02

Aim

To make Business Analysts, Project Managers and Program Managers ready to work on Agentic AI projects: grounded in how LLMs and coding agents behave, and able to own specification, clarification, planning governance, quality gates, delivery evidence and convergence with GitHub Spec Kit while a coding agent performs the implementation.

03

Audience

This program is designed for:

  • Business Analysts: who shape business intent, write and challenge the specification, and own acceptance.
  • Project Managers: who turn approved specifications into controlled delivery and own release evidence.
  • Program Managers: who set reusable standards and governance across projects.
It is a non-coding track. Participants are expected to become effective owners of the BA / PM / Program Manager layer of a Spec Kit project, not software developers.
04

Learning Outcomes

By the end of this program, participants will be able to:

  • Explain how LLMs and coding agents work, where they fail, and why agent-led delivery needs explicit, testable intent.
  • Use a project constitution and a business-first specification, with clarification as a formal quality step, to settle what is being built and why before planning.
  • Review a plan, requirements checklist, tasks and analysis output as delivery-quality gates without needing to code.
  • Supervise a coding-agent implementation and use convergence to confirm the build matches the specification.
  • Apply the workflow to a payments, merchant or financial-services scenario aligned to Fiserv's business domains.
05

Entry Guardrails

Participants should have:

  • Working experience as a Business Analyst, Project Manager or Program Manager on software or digital delivery projects.
  • Familiarity with requirements, acceptance criteria and delivery planning artefacts.
  • Basic familiarity with GitHub or a similar collaboration tool is helpful.
  • No coding skill and no prior experience with AI or LLMs is required.

Our Approach

A project-readiness bootcamp

The program is a project-readiness bootcamp, not a command demonstration:

  • Foundations first: two hours on how LLMs and coding agents work, so participants know what the agent will do with their specification.
  • One project end to end: teams take a fictional payments use case from business problem through every Spec Kit stage to a converged build.
  • Role-based: BAs, PMs and Program Managers each own their layer of the work at every stage.
  • Mostly hands-on: roughly 30% framing and facilitator demonstration, 55% guided team work and project building, and 15% review.
Our Learning Framework

Learn → Practice → Apply → Review → Refactor

Each stage runs the same cycle: a short input (Learn), guided work on the project (Practice and Apply), a review against a stated standard (Review), and a correction where the work falls short (Refactor).

01

End-Goal Project

Payment Dispute Resolution Workbench. a fictional Fiserv-aligned internal workbench for payment operations. A payment-operations analyst needs a simple internal application that receives a disputed transaction, shows the transaction and merchant context, classifies the dispute reason, retrieves the relevant policy guidance, recommends the next action and records a human decision. It is a training scenario, not a description of an internal Fiserv system or process.
02

Business Need and SDD Design Constraints

Business NeedSDD Design Constraint
Reduce time spent triaging routine payment disputes.The solution must help an analyst reach a defensible next action quickly.
Support card / merchant / digital-payment context.Use synthetic transaction, merchant and policy data; no real customer or card data.
Avoid autonomous financial action.The system can recommend and prepare a case, but a human approves any operational decision.
Provide evidence.Every recommendation must show the policy / data evidence used.
Handle ambiguity safely.If required evidence is missing or policy is unclear, route to manual review rather than invent an answer.
Be measurable.Success criteria must be measurable without depending on a specific programming language or framework.
03

Project Artefacts Produced

  • LLM behaviour notes and an ambiguity list - what an agent would otherwise have to guess
  • constitution.md - payments-domain project principles and non-negotiables
  • spec.md - user scenarios, functional requirements, entities, assumptions and measurable success criteria
  • Clarified specification - ambiguity resolved before planning
  • plan.md - implementation approach reviewed by the PM / Program Manager
  • Requirements checklist - reviewer-owned quality gate
  • tasks.md - dependency-ordered delivery breakdown
  • Analysis report - conflicts and gaps reviewed before implementation
  • Working project - produced by the coding agent from the approved artefacts
  • Convergence result - evidence that the implementation matches the specification

Why this matters. In agent-led delivery the coding agent acts on what BAs, PMs and Program Managers write, so participants first need to know how the model “reads” their words.

How an LLM produces an answer. Next-token prediction from very large amounts of text; tokens and the context window; temperature and why the same prompt gives different answers. Live demo: one prompt run three times.
25–35 min
Models and their limits. How models differ on speed, depth and cost; knowledge cut-off; no view of your systems or data unless connected; why long conversations drift.
35–55 min

What participants must understand at each stage

The learning point, the non-technical review questions and the evidence expected at each Spec Kit stage.

ConstitutionA constitution is a persistent project governance layer, not a feature requirement.Which principles must every feature obey? What can never be delegated to an agent? What evidence is mandatory?Approved project principles and gates

Project Deployment Readiness Checklist

  • Can explain how LLMs and coding agents behave, and why that makes explicit specifications necessary.
  • Can explain the full production Spec Kit path and why each quality gate exists.
  • Can distinguish business specification from technical planning.
  • Can identify ambiguity that must be resolved before implementation.
  • Can review generated requirements for testability and measurable business outcomes.
  • Can interpret plan.md and tasks.md sufficiently to challenge scope, dependencies and evidence.
  • Can use a checklist as a requirements-quality review artefact rather than a project completion tracker.
  • Can use analyze output to fix the correct source artefact.
  • Can supervise a coding-agent implementation without drifting into unapproved scope.
  • Can use convergence as acceptance evidence rather than assuming 'the demo works' means 'done'.
  • Can apply the workflow to a new payment, merchant or banking operations scenario.
